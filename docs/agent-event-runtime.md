# 事件驱动的 Agent 运行时（提案）

> 状态：提案，待评审　｜　作者：Ru41 维护者　｜　日期：2026-11-05
> 参考：AWS Research 的 [Infinity Runtime](https://github.com/hydro-project/infinity)（RAP 协议）——把 Agent 当无栈协程：对话历史即 continuation，工具调用即 await 点。
> 本文不是照搬那份设计，而是**评估它对我们意味着什么、我们取哪一部分、代价在哪**。

---

## 0. 一句话

把"外部世界发生了一件事"（签到窗口开了、录音转写完了、课表变了、爬到新内容）
从**另发一条通知消息**升级为**注入 agent 线程上下文的事件**；同时让**长工具立即返回、结果异步投回**。

目标不是切片化，而是让 agent 线程能**被打断后继续**，而不是**被通知后重来**。

---

## 1. 动机：今天真实踩到的三个问题

| 现象 | 根因 | 现行绕法 |
|---|---|---|
| 学习通手势签到只有 2 分钟窗口，人不在手机边就错过（今天丢了一次） | 通知是**另发一条 QQ 消息**，agent 线程与此毫无关系 | 无 |
| 课堂录音转写完，只能**另起一个新任务**让 agent 写笔记 | 同上：转写结果是"新任务"，不是"原线程的后续" | 无 |
| 问「单项励志金」，模型在**同一轮里**下载 61MB 学生手册 PDF 逐页渲染，300s×3 超时烧光预算 | 我们**管不住模型在一轮内部干了什么**（CLI 黑盒） | `TOOL_EXECUTION_BUDGET=24` + 系统提示词禁止下载大文件（打补丁） |

三个问题指向同一件事：**我们只能"起一轮 agent"，不能"在 agent 的历史里追加一个事件"**。

---

## 2. 现状盘点

对照 Infinity 的设计，逐项核对我们已有的：

| 能力 | 我们的状态 | 位置 | Infinity 对应 | 差距 |
|---|---|---|---|---|
| 等待不占资源（持久化执行） | ✅ 有。任务在库里排队，worker 领用、lease 心跳、崩溃可恢复 | `src/runtime/worker.rs`、`migrations/002_execution.sql` | slice 休眠 | **我们天然更省**：27 个 ru41 容器常驻，不是 per-agent 进程 |
| 至少一次投递下的幂等与顺序 | ✅ 有。`request_key` 幂等、lease + heartbeat、delivery 退避重试 | `src/ports/storage.rs`、`src/runtime/dispatcher.rs` | `StateStore` processed ids | 等价 |
| 结果回到用户 | ✅ 有。`delivery` 文档 → 渠道投递 | `src/runtime/dispatcher.rs` | — | 这是**通知**，不是**事件** |
| 线程 / 子代理 | ❌ 无 | — | `spawn_thread` / `child_of` / `report_to_parent` | 缺 |
| 事件注入 agent 历史 | ❌ 无。外部事件只能另发消息 | — | 合成工具调用 `receive_event__injected` | **核心缺口** |
| 长工具立即返回、结果投回 | ⚠️ 半有。lecture 插件自建了异步队列（handler→pending 文档→worker 轮询转写→再入队 agent），但那是**插件私有协议**，agent 侧仍是黑盒 | `plugins/lecture/src/` | `execute` 立即返回 | 缺通用机制 |
| 切片（一次模型调用为粒度） | ❌ 无。一次任务 = 一个子进程跑完整轮。**生产底座是 pi**（`ru41 qq run --backend pi`，MiniMax-M3），codex 是备用；两个底座都是黑盒进程——pi 走 stdio JSON 行协议，我们能看到 tool_call 事件、token 用量、会话 id，但**插不进它的历史** | `src/ports/agent.rs`、`src/adapters/agent/pi/`、`src/adapters/agent/codex/` | slice | **建议不做**（见 §7） |

一句话：**他们最难的一半（持久化、幂等、顺序）我们已经有了；我们缺的是"事件进历史"和"工具异步返回"，而后者被 CLI 黑盒卡住。**

---

## 3. 方案

三块，**可独立落地、独立回滚**，按价值排序。

### A. 事件注入（核心底座，价值最大）

**定义**：新增"线程（thread）"概念——一个 agent 对话上下文；新增"事件（thread_event）"——一件外部世界发生的事。
事件有两种投递方式：

- **A2（先行，可立即做）**：事件作为**下一轮的用户消息**注入该线程，附带来源、时间戳、以及线程摘要。
  语义上等价于"告诉 agent 又发生了一件事"，只是不能伪造工具调用。
- **A1（目标形态，需底座升级）**：像 Infinity 那样，运行时**伪造一条 assistant 工具调用**
  （专用工具名如 `__event__`，参数里带 `origin` 与 `origin_id`），再把事件内容作为该调用的 tool_result。
  模型看到的是一段自然的"工具调用 → 结果"，能直接复用后训练学到的"读工具结果"能力。
  **前提：必须自己掌握模型循环**（直连模型 API），我们现在是 CLI 黑盒，插不进去。

**事件来源**（首批，全部是已经在跑的插件）：

| 来源 | 事件 | 触发点 |
|---|---|---|
| 学习通签到 | 签到窗口开启 / 窗口即将关闭 | `plugins/chaoxing` |
| 课堂录音 | 转写完成（含笔记落盘结果） | `plugins/lecture` |
| 教务课表 | 课表变更、下节课即将开始 | `plugins/jwxt` |
| RSS / 机会雷达 | 命中你关注方向的新条目 | `plugins/rss` |
| 页面监控 | 关注的页面内容变化 | `plugins/pagewatch` |

**事件记录**（复用 `records` 表，kind = `thread_event`）：

```jsonc
{
  "thread_id": "qq:user:3BCF…:lecture",
  "origin": "chaoxing",          // 来源插件
  "origin_id": "1000177940386",  // 来源内的实体 id
  "kind": "sign_window_open",
  "at": 1793863845,
  "summary": "手势签到窗口已开启，2 分钟内有效",
  "payload": { /* 可选：结构化细节 */ },
  "idempotency_key": "chaoxing:sign_window:1000177940386"
}
```

**投递**：worker 取任务前先查该线程有没有未消化事件；有则拼进本轮输入（同时保留原 `prompt`，不丢原任务上下文）。
事件按 `idempotency_key` 去重；已消费的打 `consumed_at`。

**通知怎么办**：事件**不替代**通知。通知仍是"人看得见的那一条"，事件是"agent 能接着想的那一条"。两条都发，互不阻塞。

### B. 长工具立即返回、结果异步投回（附属层就能做）

**约定**：一个耗时的工具，`execute` 不再等结果，而是：

```jsonc
{ "accepted": true, "job_id": "lecture-transcribe-1234", "status": "running" }
```

完成后由工具自己把结果写成一条 `thread_event`（或 tool_result）投回原线程。

**我们已有的雏形**：lecture 插件今天就是"下载→写 pending 文档→worker 轮询转写→**另起一个 agent 任务**"。
B 就是把它从"另起任务"改成"往原线程投事件"——agent 线程接着上一步（已经知道这门课、已经知道录音文件名）继续写笔记，而不是被重新喂一遍 31KB 转写 + 重述上下文。

**顺带解决**：worker 槽不再被几分钟的转写占住；`TOOL_EXECUTION_BUDGET` 这种硬压可以逐步退场。

### C. 线程隔离与子线程（最后做，可选）

事件默认交给一个临时子线程处理，父线程历史不变（Infinity 的 threaded processing）。
我们的痛点：RAG 片段 + 技能文本每次都塞进 prompt，事件一多主上下文就撑爆 → 子线程是解法。
但这依赖 A（能开子线程）+ 模型循环可控，排在最后。

## 4. 详细设计要点

**新增数据**

- `records` 表新增 kind：`thread`（线程元信息）、`thread_event`（事件）。不动既有表结构 ✓（`records` 是通用 KV，kind+id 主键）。
- 迁移：只加索引，不加表——`records` 已有 `(kind,id)` 主键，按 `thread_id` 查需要加索引：`CREATE INDEX records_thread ON records(kind, json_extract(body,'$.thread_id'))`。

**运行时改动点（核心）**

| 文件 | 改动 |
|---|---|
| `src/runtime/worker.rs` | 取任务前查线程事件；有则拼进 prompt（A2 形态） |
| `src/ports/agent.rs` | `AgentRequest` 增 `events: Vec<AgentEvent>`；`BackendDescriptor` 增 `supports_event_injection`（先 false） |
| `src/adapters/agent/pi/`（生产）、`codex/`（备用） | 把 events 渲染成输入（先按 user 消息拼接，A1 形态留接口）。两个底座都是黑盒进程，A2 形态不受影响 |
| `src/runtime/dispatcher.rs` | 通知路径基本不动；新增"事件投递"旁路 |

**附属改动点**

- 新增 `thread_id` 约定：`{channel}:{target}:{主题}`（例如 `qq:user:3BCF…:lecture`）——插件在写 pending / 事件时带上它。
- 各插件加"发事件"能力：写一条 `thread_event` 记录即可（不需要新接口，现有 `store.put_document` 就够）✓ **这条很重要：事件是附属能自己写的，不需要核心新增 API。**

**兼容**：没有事件的线程走老路径 ✓；事件默认关（配置开关），逐插件灰度 ✓。

## 5. 分阶段实施

每阶段可独立上线、可独立回滚。

| 阶段 | 内容 | 改动面 | 验证方式 | 回滚 |
|---|---|---|---|---|
| **P0** 约定与观测 | 定义事件协议（kind/字段/来源约定），插件侧只写事件不消费 | 附属（只写 `thread_event` 记录） | 库里有事件、agent 行为不变 | 关掉开关 |
| **P1** 事件旁路 | worker 消费事件 → **仍然只发通知**，不改 prompt；同时打印"这条线程有 N 个未消化事件" | 核心（worker 读事件，不注入） | 日志里能看到事件流；用户侧行为不变 | 停消费 |
| **P2** 事件注入下一轮（A2） | 事件作为下一轮用户消息注入该线程 | 核心（worker + agent request + 适配器） | 用学习通签到窗口做端到端：窗口开 → agent 线程收到事件 → 决定动作 | 关开关（回到 P1） |
| **P3** 长工具异步返回（B） | lecture/下载类工具改 `execute` 立即返回 + 完成投事件 | 附属（插件内部改造）+ 核心（工具结果落为事件） | 录音转写期间 worker 槽不阻塞；转写完原线程直接续写 | 插件级开关 |
| **P4** 直连模型 API + 合成工具调用（A1） | 底座从黑盒进程换成自有循环，事件以伪造工具调用注入 | 核心（较大）。前提是我们自己掌握模型循环——现在的 pi/codex 都是黑盒（pi 只有 stdio 事件流，没有"往你历史里插一条"的接口） | 事件在历史里呈现为自然工具调用；模型行为对比 | 保留 CLI 路径双跑 |
| **P5** 子线程隔离（C） | 事件默认子线程处理 | 核心 + 底座 | 长会话不被事件冲垮 | 默认 inline 模式 |

**建议顺序**：P0→P1（附属可独立做，零风险）→ P2（核心，第一次真正吃到收益）→ P3（附属，收益立竿见影）→ P4/P5（视 P2 的实际效果再定）。

## 6. 优点

**架构收益**
1. **agent 线程能"被打断后继续"**：签到窗口开了、录音转写完了，agent 接着上一个上下文推理，而不是被另起一条消息打断。
2. **工具执行时间与 agent 逻辑解耦**：长工具不占 worker 槽；一个任务可以包含"等 3 天的 CI"这种现实。
3. **上下文可控**：事件可选择进主线程还是子线程；配合 B，历史不再被一次性灌满。
4. **与我们的强项对齐**：我们已有持久化执行与幂等队列，事件模型是**在既有底座上加一层**，不是重写。

**工程收益**
5. **省掉一堆补丁**：TOOL_EXECUTION_BUDGET、"[qq] 正在输入"这类补偿机制可以逐步退场。
6. **插件自治**：事件是 `records` 里的一条记录，**附属自己就能发**，不需要核心新增 API（除 P2 的消费端）。
7. **可观测**：事件流天然是审计日志——"这个线程发生过什么"一目了然（今天的段错误事故就查不到这类线索）。

**用户体验**
8. 签到窗口这种**短窗口事件**能被及时唤醒并立即行动（而不是靠人看通知）。
9. 录音转写完立刻整理笔记并通知，中间不用再喂一遍转写全文。

---

## 7. 缺点与成本（诚实版）

**架构复杂度**
1. **多一套概念**：thread / thread_event / 事件注入规则，会让"消息去哪了"变复杂——今天已经有"任务队列 / 通知队列 / 事件表"三处，再加一层要小心。
2. **两条通道容易打架**：通知（给人）与事件（给 agent）同时存在时，用户可能看到"机器人没反应"其实是事件在后台处理 ✓ 需要在回执里说清。
3. **事件顺序与去重**：at-least-once 投递下，事件可能重复或乱序；幂等键要设计对，否则 agent 会对同一件事反应两次。

**存储与性能**
4. **历史读写成本**（Infinity 自己也没给数据）：我们的 prompt 平均 4.6KB、最大 31.4KB（课堂录音整段转写）；codex 的真实历史在它自己的 rollout 文件里（今天一天 24MB / 18 个会话）。**我们的 continuation 现在劈成两半**，事件注入前应先归一，否则每轮都要在两处拼装。
5. **事件注入会挤占上下文**：事件多了要么撑爆窗口，要么稀释注意力——这正是他们用子线程的原因，我们若先做 A2 会更明显。

**模型质量风险**
6. **合成工具调用是"骗"模型**：Infinity 靠后训练让模型认这套格式；我们若直连模型 API（A1），得确认目标模型对伪造调用不反感/不误解——这是**要实测**的，不是想当然。
7. **A2 形态的语义偏差**：事件伪装成"用户说的"，模型可能当成用户指令（他们文档里明确讨论过这个坑：`validate_*` 形态、塞进系统提示会丢时间序）。A2 必须**显式标注来源与时间**。

**迁移成本**
8. **P4（直连模型 API）是最大的一块**：现在的 pi 与 codex 都是黑盒子进程（pi 走 stdio JSON 行协议，能观测不能注入）；改成自有循环意味着重做两套底座的适配、工具协议、会话续跑。这是核心组的活，不是附属能做的。
9. **改造现有插件**：各插件要产出事件、带上 thread_id，涉及面广（今天涉及 5 个插件）。

**"过度设计"的风险**
10. **我们的规模其实不需要完整切片化**：203 个任务、平均 prompt 4.6KB、27 个常驻容器。Infinity 的核心卖点（8 万 agent / 树莓派）解决的是**我们暂时没有的问题**；照搬会引入复杂度却不产生收益。
11. **"等了 3 天不耗资源"我们已经有了**（任务在库里排队，不占进程）——所以那条最性感的收益对我们近乎免费。

---

## 8. 结论：利大于弊？

**分层结论，不是一句"是"或"否"。**

- **整套照搬（切片化 + 自有模型循环）：利小于弊。** 我们的任务量、prompt 体量、容器形态都不需要它；P4 的成本远大于收益。
- **只取 A（事件注入）+ B（长工具异步返回）：明显利大于弊。**
  - 收益有今天三个真实事故撑着（签到错过、转写断链、模型烧预算）；
  - 成本大头在**核心**（P2 约一周），**附属侧几乎零成本**（事件就是一条记录）；
  - 且**可分阶段、可灰度、可回滚**：P0/P1 纯附属、零风险；拿到 P2 的实测数据再决定 P4。
- **判断被推翻的条件**（出现任一就停）：
  1. P2 实测显示事件注入让 agent 的回答质量下降（错认事件为用户指令、重复响应）→ 退回通知模式；
  2. 事件流量的实际规模远大于预期（每天几十上百条），上下文管理成本超过收益 → 只保留"短窗口事件"这一类；
  3. 核心组把底座换成自有模型循环的计划落空 → A1 长期不可达，A2 的收益不足以支撑复杂度。

**推荐决议**：批准 **P0 + P1**（附属侧，今天就能做，零风险），**批准 P2 立项**（核心，一周），
**P3 与 P4/P5 暂缓**，等 P2 的实测数据。

---

## 9. 明确不做什么

- 不做切片化（一次模型调用为一个 slice）——我们的规模不需要。
- 不做 per-agent 常驻进程——我们已经是"任务在库里、进程在池里"。
- 不替换现有通知机制——事件是**新增通道**，不是替代。
- 不在附属里自己造模型循环——那是核心底座的决策（另见我们给核心组提的 issue）。
