# AI 规划、人类学习：目标函数与系统架构

> 定位：**AI 是规划者，人是学习者。**
> 目标不是"给人做个日程助手"，而是——**在有限时间里，规划出对你最好的学习安排。**
>
> 这篇把"最好的"变成一个**可算的量**，并给出 Ru41 的实现架构。
> 相关：[learning-scheduling.md](learning-scheduling.md)（FSRS 与记忆层）、[portfolio.md](portfolio.md)（多目标分层）、[longterm-planning.md](../longterm-planning.md)（排期机制）。

---

## 1. 这是带约束的最优化，不是"排个日程"

```
maximize   Σ_g  w_g · Δprogress_g(t)      ← 每个目标的推进量 × 它的权重
         + Σ_k  Δretention_k(t)          ← 每个知识点的记忆挽回量

subject to
   Σ t(t) ≤ T_available(t)               ← 时间预算（课表扣除后）
   t_g(t) ≥ min_g                        ← 每个目标的最小投入（否则永远学不会）
   复习间隔 = FSRS 最优间隔               ← 记忆层约束
   每日认知负荷 ≤ L                       ← 可持续性约束
   不跨越已占用时段                       ← 课表/日程约束
```

`w_g` 是目标权重（人给），`Δprogress_g` 是里程碑推进量，`Δretention_k` 是 FSRS 的记忆挽回量。

**难点全在"两个 Δ 能不能放到同一个尺度上比"** —— 见 §3。

## 2. 三件套（都有学术先例）

| 组件 | 先例 | Ru41 实现 | 状态 |
|---|---|---|---|
| **学习者模型**<br>（我当前会什么、状态如何） | [The Imperfect Learner](https://arxiv.org/abs/2511.05903)（记忆 + 发展轨迹 + 元认知 + 人格） | FSRS 记忆状态 + 里程碑进度 + 精力/心情记录 | **FSRS 部分已有** |
| **内容仓库**<br>（能学什么、按什么顺序） | [ExpertAgent](https://arxiv.org/abs/2510.07456) 的 "validated curriculum repository"；[KG 课程建模](https://arxiv.org/abs/2501.12300) | **长期规划文档**（Vault `08-Planning-规划/Plans-计划/`）：人写目标/验收/停止条件，AI 补 step 流 | **原型已跑通**（`scripts/ai-planner-sim/` + `src/plan.rs`） |
| **动态规划器**<br>（下一步学什么、怎么学） | ExpertAgent 的 "dynamic planning based on continuously updated student model" | LLM 出 step 流（名字+时长）→ 确定性装箱（可跨块切分） | **分工已跑通** |

### 2.1 ExpertAgent 有一句话点破了关键设计

> All instructional content is grounded in a **validated curriculum repository**, effectively reducing hallucination risks in large language models.

**LLM 的输出必须锚定在受验证的内容仓库里**（Vault 笔记、课表、已拆解的知识点），不能自由发挥。
这跟 Ru41 既有哲学完全一致——LLM 只做相关性和文案，判定归确定性代码。

### 2.2 但先例做的都是「课程内」规划

Academic-Curator、ExpertAgent 这一类都在**一门课 / 一个知识图谱内部**给知识点排序。
**Ru41 的场景是跨目标**：六级、雅思、HICP、高数、Rust、背书同时进行，还要抢同一批晚上和周末。

**这一层学术上基本没人做**（因为真实学习者不会同时学 6 门）——所以 Ru41 要做的增量在这里：

```
课程内排序（先例做的）           跨目标资源分配（Ru41 要做的）
   知识点序列                          每个目标分多少时间
   ↓                                  ↓
   「这个知识点什么时候学」     +    「这周该偏向谁」
```

**拼接的关键：两者共用同一个时间预算，但产出单位不同**（离散序列 vs 连续额度）。

## 3. 核心设计：把两种单位接通

### 3.1 问题

- **碎片复习**的收益：FSRS 直接给 —— 这次复习把留存率从 0.6 提到 0.95，**ΔR = 0.35**
- **整块学习**的收益：推进了某个里程碑 —— 但这是"一个 Rust 块学完能写 `minigrep`"，**单位完全不同**

不统一就没法比较，没法比较就没法优化。

### 3.2 解法：统一成「每分钟挽回的知识量」

```
碎片单位收益 = ΔR_k / minutes          ← FSRS 给，可算
整块单位收益 = Δprogress_g / minutes    ← 里程碑定义，可算
```

于是整块分配退化成一个**背包问题**：按单位收益排序，依次填入可用整块。

### 3.3 Δprogress 怎么定义（这一步最容易出错）

必须**可验收**，否则又回到"不可测量"。定义方式：

| 里程碑类型 | Δprogress | 验收方式 |
|---|---|---|
| 读（Rust Book 一章） | 该章的「自测题通过率」变化 | 跑示例代码的测试 |
| 练（题型专项） | 该题型正确率变化 | 做一套题 |
| 考（四级/雅思） | 模考分数变化 | 模考 |

**注意**：Δprogress 里**必须含 LLM 的拆解质量**（里程碑拆得对不对，直接决定 Δprogress 是否真实）。
这是整个系统里最需要 agent、也最容易出错的地方。

### 3.4 一个具体的数（来自真实模拟）

[learning-scheduling.md §3.4](learning-scheduling.md) 的实测：碎片池 13 分钟/天能维持 300 张卡 90% 留存，
**每天只需 1.4 分钟**就能拿到约 0.9 的留存率。

也就是说：**碎片单位收益 ≈ 0.9 ÷ 1.4 ≈ 0.64 记忆量/分钟**。
一个 2 小时的整块，如果推进了一个「Rust Book 章节 + 测试全过」的里程碑（Δprogress = 1.0），
单位收益 = 1.0 ÷ 120 ≈ 0.008 —— **比碎片低两个数量级**。

> **这说明什么？** 碎片复习的"单位收益"虚高，因为它只维持既有记忆；
> 而整块学习产生的是**新增能力**（两者不同质，不能直接比）。
> **所以不能简单按单位收益排序。**
>
> 正确的做法是**分层目标函数**：
> ```
> 第一层（硬）：记忆维持 —— 碎片时间优先保证每张卡的 R 不跌破阈值
>              （否则第一层不满足，后面都没意义）
> 第二层（软）：剩余整块按 Δprogress 的绝对值 + 权重排
> ```
> **记忆维持是约束，不是目标。** 这一条跟 §4 的先例一致：FSRS 负责的是"别忘了"，
> 整块负责的是"变强"。

## 4. 跨目标的价值比较：只能靠权重近似

碎片 vs 整块解决了（分层）。但**"背书知识点" vs "学 Rust"** 谁更值？这本质是主观的。

**处理方式**（也是这个系统唯一需要人持续输入的东西）：

| 人的输入 | 形式 | 更新频率 |
|---|---|---|
| 目标权重 `w_g` | 每个目标 0-100 的标量 | 每周回顾时调整 |
| 外部锚点 | 考试日 / 报名截止 | 一次性 + 变动时 |
| 作息与不可用时段 | 每日可排期区间 | 偶尔（如选课期） |
| 精力状态 | 主观 1-5 或"今天状态差" | 临时 |

**其余全部由 AI 决定**：具体哪天、哪个块、复习哪几张卡、什么时候重排。

这跟 Reclaim 2.0 的 Preview Mode 是同一个思路，但更进一步：
Reclaim 是"AI 提议、人批准"；这里是"**AI 规划、人只给权重和锚点**"。

## 5. 系统自评估回路（规划器必须能被检验）

"AI 规划"意味着**你必须能判断这次规划好不好**。所以要有回路：

```
规划 → 预测效果（FSRS 预测 R；里程碑预测进度）
     ↓
执行 → 记录实际（复习评分、测试结果、模考分数）
     ↓
对比 → 预测 vs 实际 的偏差
     ↓
修正 → 调 w_g / 调目标留存率 / 调拆解策略
```

**这一步是"AGI 那一层"的现实替代品**：不需要通用智能，需要的是
**每个组件都可预测 + 偏差可观测**。

对应我第一轮调研到的 [CORAL](https://arxiv.org/abs/2610.40350)（checkpoint 工作记忆）和
[Seq@K](https://arxiv.org/abs/2610.37859)（评估"模型如何从反馈迭代"）——
它们做的就是"让 agent 的自我改进可测量"。

## 6. Ru41 实现分解

| 组件 | 位置 | 类型 | 依赖 |
|---|---|---|---|
| 记忆状态与最优间隔 | `fsrs` crate v7 | 纯算法 | 已验证可编译 |
| 空闲计算与槽位推荐 | `src/domain/availability.rs`（新） | 纯函数 | 已有算法（scripts/plan-sim.py） |
| 里程碑定义与 Δprogress | `goal` kind + agent 拆解 | agent + 存储 | 需新做 |
| 权重与锚点 | `goal` kind 字段 | 存储 | 需新做 |
| 跨目标分配（背包） | `src/domain/allocation.rs`（新） | 纯函数 | 依赖上面两项 |
| 每周回顾推送 | `run_periodic` + 通知 | 现有机制 | 已有 |
| 重排（课表/日程变化后） | 现有事件机制 + 平移策略 | 混合 | 已有 |

**几乎所有决策逻辑都是纯函数**——这是 Ru41 既有哲学的延续，也是这个系统能被测试、被回滚的原因。

## 7. 诚实的边界

1. **Δprogress 的定义依赖 LLM 拆解质量。** 拆错了，整个单位收益尺度就错了。
   这是全系统最脆的一环 —— 而它恰好是 LLM 该干的活。
2. **跨目标的价值比较本质主观**，只能靠人给权重近似。系统不能消除这个，只能让它更容易表达。
3. **坚持度无法建模。** "这周说好每天学 2 小时，实际只学了 1 小时" —— FSRS 的记忆层能反映
   （没复习的卡 R 会掉），但"要不要继续做 Rust"这种决策做不到。
4. **先例都是课程内规划**，跨目标的分配没有现成方案可抄，需要自己定义并验证。
5. **目标留存率是个旋钮**：85% → 98% 意味着复习量翻 7 倍（实测 492 → 3620 次）。
   这个取舍是人的判断，不是算法能替你定的。

> 抓出了自己规划器的 3 个 bug，并证明**这组目标在学期内不可行**）。

| # | 做什么 | 验证什么 |
|---|---|---|
| 1 | 从**一篇课堂笔记**生成 20 张卡，FSRS 跑一周 | 学习者模型的数据源通不通 |
| 2 | 定义 3 个目标的里程碑 + Δprogress（手写，不自动） | 目标函数能不能算 |
| 3 | ~~手写一个"跨目标背包"原型~~ | ✅ 已完成，见 ai-planner-sim.md |
| 4 | **填真实锚点后重跑模拟** | 真实目标组合到底可不可行 |
| 5 | 把「可行性诊断 + 取舍建议」做成 CLI 命令 | 这两个是 AI 规划器的核心输出 |

**不要**一开始就追求全自动。①② 两步都能手工验证，
验证通过再自动 —— 这也是 Ru41 一贯的做法（校园跑插件是薄接入层，判断归服务端）。

### 8.1 模拟已经确立的三条硬规则

1. **分配顺序必须是：硬锚定 → 软基础量 → 跟课 → 日常**。
   硬约束必须先于弹性项，否则跟课型会把整块资源吃光、把硬锚定目标饿死（模拟实测 bug）。
2. **可行性诊断是必要输出**，不是附属功能：需求 69 块 vs 可用 13 块时，
   正确行为是说"不可行"并给取舍选项，而不是排出一堆做不到的日程。
3. **取舍排序可以纯规则算出**（释放块数 ÷ 权重），人只需要在几个选项里挑。
