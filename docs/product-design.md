# Ru41 产品设计

**产品形态：** 运行在个人服务器上的自动化助手。
**技术基础：** Rust 宿主 + 可扩展 Agent 底座，Codex 为首个实现。
**设计状态：** 概念与首版范围设计，具体交互和接入能力待验证。

> 在宿舍服务器上运行，围绕 Obsidian 建立「采集 → 筛选 → 加工 → 审核 → 行动 → 复盘」的个人工作流，覆盖学习、科研、项目、校园生活、机会发现和内容创作。

## 1. 产品定位与目标

- 面向个人长期使用，先服务本科生活、AI 安全方向学习与项目实践。
- Obsidian 是知识与决策入口，统一保存个人想法、采集的一手信息、来源、结论、行动项和复盘；换服务器或模型后仍能独立使用。
- 自研应用、后台服务、工具与编排逻辑统一使用 Rust，负责调度、采集、去重、任务状态、Codex 会话管理、文件写入和推送。
- Codex 是首个运行时 Agent 底座，通过统一 AgentBackend 接口接入，负责理解目标、拆解任务、推理、选择工具、分类、摘要和内容生成；Rust 提供可调用工具并执行权限与状态校验。金额计算、日期比较和重试由 Rust 完成。
- 人负责重要决策：作业提交、公开发布、资金操作、笔记合并删除和实质重写保留审核环节；规则明确的 Inbox 整理与归档自动执行。
- 信息输出需要回答：发生了什么、证据在哪、为什么与我有关、接下来能做什么。
- 视频、照片、数据集、模型、数据库和运行日志不进入 Vault，Vault 只保存相关索引与链接。

## 2. 核心使用场景

目标用户是同时处理课程、科研、个人项目和内容创作的本科生，首个用户是自己。

| 场景 | 用户需求 | 产品交付 |
|---|---|---|
| 每天开始学习前 | 快速知道今天值得关注和必须处理的事 | 一份包含截止事项、精选信息和待办的每日简报 |
| 随手记下想法或保存链接后 | 减少整理负担，之后能找回来 | Git 同步后自动整理归档，附关联笔记与处理记录 |
| 看到论文或 X 上的新信息 | 判断是否值得花时间深入 | 原始来源、核心结论、个人相关性和下一步建议 |
| 作业临近截止 | 掌握要求与进度，检查解答 | 作业清单、带依据的草稿、审核后提交结果 |
| 宿舍余额不足 | 及时获知并处理 | 带查询时间的余额提醒 |
| 每周复盘 | 看清完成了什么、哪里停滞 | 有记录依据的周报与可调整的下周计划 |
| 准备写文章或做视频 | 把已有积累变成可修改的内容 | 选题、文案、字幕或素材索引草稿 |
| 服务器任务异常 | 知道影响与恢复方式 | 失败原因、最后成功时间和重试入口 |

产品价值通过持续使用判断：是否减少了重复整理、是否发现了有用信息、是否帮助完成了实际行动。

## 3. 功能模块

### 3.1 Git 更新触发的 Obsidian 自动整理

**核心体验：把临时想法写进 Inbox，完成 Git 同步后，Ru41 自动整理并放到合适位置。个人想法和采集到的一手信息共同沉淀在 Obsidian。**

#### 触发与反馈

```text
本地 Obsidian：记录临时想法到 Inbox
                    ↓
              Git 提交并推送
                    ↓
Rust 后端发现新提交并同步服务器 Vault 副本
                    ↓
识别 Inbox 新增/修改内容 → Codex 理解与分类
                    ↓
Rust 校验归档位置 → 整理内容、标签和关联 → 自动归档
                    ↓
Git 提交并推送整理结果 → 本地同步后在 Obsidian 查看
```

- Rust 后端负责发现更新，Git 本身不承担任务调度。首版建议定时检查远端新提交；具备接收条件后可增加经校验的 webhook 或自托管仓库 hook，定时检查作为补漏。
- 只有服务器成功取得对应提交后才创建整理任务；连续提交合并处理，减少中间版本的重复整理。
- 用户无需逐篇点击确认。分类明确、目标路径符合配置且无冲突时，自动整理和移动。
- 整理完成后记录“哪些笔记移动到哪里、补充了什么、哪些需要补充信息”，普通结果合并通知。
- 分类不明确或有冲突时，原笔记留在 Inbox 并说明原因；用户可以补充说明、指定目录或稍后处理，其他笔记继续归档。

#### 内容整理与归档规则

- 输入：`00-Inbox-收件箱/` 中新增或内容更新的 Markdown 笔记，包括随手想法、摘录、链接和粗略计划。
- Codex 结合笔记内容、已有目录、个人关注方向和相关笔记，给出分类、标题、摘要、标签、关联与目标目录；Rust 校验并执行。
- 自动整理包括分段、补充标题层级、标签、简短摘要和关联链接，保留个人原始表达与细节；新增解释或推断明确标注为 Agent 补充。
- 按类型归档：课程 → `01-Courses-课程/`；项目 → `02-Projects-项目/`；知识与论文 → `03-Knowledge-知识/`；机会 → `05-Opportunities-机会/`；自动化设计 → `06-Automation-自动化/`；选题 → `07-Blog-博客/Ideas-选题/`；计划 → `08-Planning-规划/Plans-计划/`。
- 只使用已配置的目录和命名规则；默认保留文件名，重名时生成唯一名称，不覆盖已有文件。
- 移动笔记时修复可解析的双链、Markdown 相对链接与附件引用；无法可靠修复时保留原位并标记原因。
- 相似笔记建立关联；涉及合并多篇笔记、拆分并删除原文、实质重写或删除内容时进入审核。
- 已归档笔记继续允许用户自由编辑；普通修改不会再次触发自动搬家。重新整理通过手动任务或明确标记触发。
- 提供 `auto_archive: false` 标记，允许正在写的长文、Inbox 说明文件或指定笔记留在原处；配置中支持排除路径。
- 空文件、模板和不支持的附件跳过；Codex 失败时保留原文并支持重试。

#### 一手信息进入同一个知识库

```text
X 原帖 / 论文 / 官方公告 / 项目动态 / 用户保存的来源
                         ↓
              采集 → 去重 → 相关性筛选
                         ↓
               来源笔记 + Agent 整理
                         ↓
      按主题或类型写入 Obsidian → 关联项目/知识/任务
                         ↓
                   Git 同步与推送
```

- 用户想法与外部信息使用相同的分类、去重、关联和写入能力，分别保留内容来源身份。
- 筛选后的外部信息自动生成 Markdown 来源笔记，无需用户再次收藏才能留存；主题明确时直接归档，需要判断时进入 Inbox。
- 来源笔记保存作者/机构、原始 URL、来源 ID、发布时间、采集时间，以及可保存的原文或关键摘录；AI 摘要、判断和行动建议单独分区。
- 标注一手来源或二次转述，能找到原始材料时补充链接；不把抓到的任何帖子都视为一手信息。
- 同一来源更新原记录或补充版本变化；不同来源报道同一事件时建立关联，保留各自证据。
- 日报引用这些长期保存的笔记，用户从摘要能回到笔记，再回到原始来源。全量抓取缓存与大型附件仍保存在服务器独立存储。

#### 同步、冲突与重复处理

- 每篇笔记采用稳定 ID，记录原路径、目标路径、输入内容指纹、处理版本和任务 ID；移动后仍可识别同一篇笔记。
- 处理状态持久化到数据库：新提交只用于发现变化，相同内容指纹且已成功处理的笔记不重复整理。
- Ru41 写回的提交记录任务标识和输出指纹，自己的整理结果不再次触发整理循环；不能只按提交作者过滤，以免漏掉混合提交中的用户更新。
- Rust 串行执行 Vault 写入与 Git 操作，写入前核对笔记版本；处理期间远端有新修改时先同步并重新校验，必要时重新整理。
- 用户本地尚未推送的编辑在后续同步时可能冲突，保留双方内容交由处理，不强制覆盖或强推。
- 只有整理结果成功提交并推送后才标记“已归档并同步”；推送失败保存待同步状态，重试发送既有结果，不重复生成笔记。
- 撤销某次归档时生成反向变更并检查后续编辑，同时记录撤销状态，避免下一轮又自动归档；不直接重置整个仓库。

### 3.2 校园生活与课程助手

**水电费**

- 适配本校水电小程序或可用查询接口，每日读取余额与查询时间。
- 保存历史读数，生成每日变化、低余额提醒和消耗趋势；区分充值造成的余额增长与实际消耗。
- 查询失败显示最后成功时间，不把旧余额当成当天结果。
- 水费、电费分别验证接入能力；首版不做自动充值。

**知到作业**

- 获取本人课程的作业内容、附件、截止时间和提交状态。
- AI 结合课程资料生成解答草稿、推导与依据，标出不确定项。
- 你审核、修改并确认具体答案版本后，系统提交该版本并保存回执。
- 登录过期、验证码、接口变化进入待处理状态；提交超时先查询平台状态，避免重复提交。
- 顺序：验证读取 → 生成草稿 → 实现审核 → 接入提交。使用范围按课程要求确定。

**复习助手**

- 根据课程笔记、作业和错题，在考试前生成复习清单与 Quiz。
- 记录薄弱知识点和复习任务，汇入个人计划。

### 3.3 论文与科研追踪

- 追踪 arXiv 分类、关键词、作者，以及选定期刊和会议的新论文。
- 通过目标期刊清单追踪 SCI/SCIE 期刊文章；收录状态、元数据和全文获取分别处理。
- 核心方向：AI Security、LLM Security、Agent Security、Prompt Injection、Tool-use Security。
- 扩展方向：AI Infrastructure、Model Training、Distributed Systems、AI Applications、Developer Tools。
- 根据 DOI、arXiv ID、版本和标题等去重，关联预印本与正式发表版本。
- 输出研究问题、方法、结果、局限、个人相关性、论文及代码链接。
- 摘要标明「基于摘要」或「基于全文」，不补写材料中没有的实验结论。
- 筛选后的论文自动保存来源与摘要笔记，并进入每日精选；深入阅读时继续补充阅读记录；跟踪 NeurIPS、ICML、S&P、USENIX 等会议动态。

### 3.4 X 与行业信息流

目标：发现一手研究、工程经验和机会信号，减少重复转述。

| 来源类别   | 候选来源                                                                 |
| ------ | -------------------------------------------------------------------- |
| 一手社交信息 | X 研究者、创始人、工程师、安全研究者及精选 Lists                                         |
| 官方动态   | OpenAI、Anthropic、DeepSeek、Google DeepMind、xAI、Meta AI 的研究、工程、安全与项目计划 |
| 开源与社区  | GitHub Trending、releases、good first issue；Hacker News、Reddit、Devpost |
| 中文补充来源 | 机器之心、量子位、安全客、先知社区，尽量追溯原文                                             |
| 安全情报   | CVE、Advisory、PoC，保存受影响版本、修复信息与原始公告                                   |

统一处理：

1. 记录原帖、作者、发布时间、采集时间和证据链接。
2. 同一事件聚合，过滤重复搬运、纯营销和缺少实质信息的发布。
3. 按个人相关性、一手程度、新增证据、时效性与行动价值筛选；热度只作辅助。
4. 输出「发生了什么 → 为什么重要 → 与我有关之处 → 下一步行动」，区分事实与推断。
5. 筛选后的信息自动写入 Obsidian 来源笔记，日报链接对应笔记；时效性强的内容单独提醒；通过有用/无用反馈调整来源与筛选规则。

X 接入需要实测，不预设完整覆盖或实时性。先评估可用 API、订阅来源和现成服务，再决定是否维护登录态采集器。


### 3.5 机会、竞赛与资源发现

共用采集能力，保留不同判断任务和数据结构：

| 类别 | 关注内容 | 输出 |
|---|---|---|
| 明确机会 | 实习、工作、科研、奖学金、交流、校内项目、开源贡献 | 机构、资格、截止时间、方向匹配、申请入口与下一步 |
| 竞赛 | CTF、大厂赛事、学校赛事、Hackathon | 报名与比赛时间、组队人数、赛道、学校认定等级、难度、年级适配、时间冲突 |
| 收入与节省成本 | SRC/Bug Bounty、免费 AI/GPU 资源、开发者计划、学生优惠、开源赞助、二手转售、新平台机会 | 条件、成本、有效期、收益依据、行动步骤与不确定性 |

- 过期机会不作为新推荐，重要变更更新原记录，报名截止单独提醒。
- 学校认定等级和资格依据原始通知，不让模型猜测。
- 收益估计必须带依据，未知则留空。
- 量化方向保留为策略学习和模拟盘研究；资金执行不属于首版自动化范围。
- SRC 候选：小红书、360、新东方、知乎、B站、淘宝、京东、美团、字节、腾讯。这里只是待核验信息源，不视为自动授权测试目标。
- 资源候选：GitHub Education、Colab、Hugging Face、OpenAI 研究/额度计划、阿里云与腾讯云学生资源、AWS Educate、Azure for Students。当前资格、额度与可用性接入时核实。

### 3.6 GitHub/Gitee 项目状态

- 同步指定项目的 README、description、language、topics、stars/forks、issues、releases、recent commits 和更新时间。
- 生成项目进展摘要、贡献统计，按需监控 Star 变化。
- 自己的项目状态写入 `02-Projects-项目/`，外部项目动态进入信息筛选管线。
- Vault 保存项目索引与进展，不复制代码、依赖、构建产物或项目 `.git`。
- 保留人工项目描述；不能把 commit 数直接当成实际完成的工作。

### 3.7 规划、周报与财务

- 汇总课程截止事项、项目任务、比赛、申请和阅读计划，给出每日/每周安排建议。
- 根据日志、课程笔记、Git 活动、项目进展、机会跟进和参赛记录生成周报。
- 周报区分已完成、进行中、阻塞和下周建议，链接真实记录；没有记录就明确说明。
- 月报关注长期方向、投入分配和阶段目标变化。
- 财务通过手动录入或账单导入建立收支记录，做分类、预算对比和周期汇总。
- 金额由程序计算，AI 可建议分类和解释；重复导入不重复记账。
- 个人财务记录已经发生的收支，收入机会记录尚待评估的可能性，两者分开。
- 周报文件使用 `2026-W42.md` 这类含年份的名称，避免跨年覆盖。

### 3.8 博客、自媒体与媒体资产

**文字链路：** 笔记/项目经验 → 选题 → 草稿 → 人工修改审核 → 发布 → 回填链接。

- 人决定选题，AI 可提供建议，支持中文和英文草稿。
- 草稿写入 `07-Blog-博客/Drafts-草稿/`。
- 审核后部署博客，GitHub Pages 保留为候选；确认部署成功才标记 published。

**媒体链路：** 手机照片/音视频 → 独立媒体存储 → 转写与索引 → 文案/字幕/素材建议 → 人工审核 → 成片或文章。

- 近期：语音转文字、分段、字幕、标题与简介、视频转文章、口播稿。
- 后续：分类、场景识别、OCR、人物/地点/事件标签、精彩片段筛选、粗剪与多平台发布。
- Vault 保存素材索引、日期、地点、事件、关键词、拍摄日志、Vlog 项目、成片链接和时长。
- 原素材、转码文件和成片放 NAS、硬盘或对象存储，按日期与 Raw/Selects/Projects/Published 分层。
- 人物信息按需脱敏，发布前检查私人资料；识别失败进入待处理，空间不足告警。

### 3.9 终端与服务器操作

- 首先提供服务器状态、磁盘空间、任务状态和日志查询。
- 再支持预设任务：运行采集、重试、同步 Vault、生成日报。
- 文件修改和维护操作限制目录、命令权限、执行时长，并保存执行结果。
- 删除、系统配置变更等先展示计划再确认；外部网页和模型摘要不能直接转成 shell 命令执行。
- SSH、CLI、聊天入口逐步接入，首版保证 CLI 可独立使用。

### 3.10 消息网关：QQ、飞书与钉钉

**目标：从日常聊天工具记录想法、交办任务、查询状态、审核结果，并接收主动简报。** 三个平台共享同一套 Ru41 能力，分别作为可启停的渠道模块接入。

| 用户消息或场景 | 产品行为 |
|---|---|
| “记一下：想做一个论文复现实验……” | 保存为 Inbox 笔记，返回记录结果，进入统一自动整理归档流程 |
| 发送论文、X 原帖或项目链接并要求收藏 | 获取可访问材料，保留原始来源，生成并归档来源笔记 |
| “整理一下 Inbox” | 创建归档任务，先回复已接收，再返回处理结果 |
| “今天有什么值得看的？” | 返回精选信息，提供标题、摘要、来源与对应笔记标识 |
| “宿舍还剩多少电？” | 查询并回复余额，注明数据时间 |
| “任务进度怎么样？” | 返回当前会话关联任务，或按任务 ID 查询 |
| 收到作业或文章草稿 | 查看内容，修改、确认或退回；确认绑定具体任务及内容版本 |
| 到达简报时间或提醒条件 | 向用户配置且平台允许的接收目标发送通知 |

- 文本与链接作为首版交互；图片、文件、语音按渠道实际能力逐步支持。
- 私聊作为个人任务的主要场景；群聊通过 @ 或命令明确触发，按授权范围响应。
- 私人笔记、账单和课程资料默认只发送到绑定的个人目标，群聊中请求时不能直接暴露私人内容。
- 普通聊天不会全部写入 Obsidian；明确“记一下”“收藏”或配置的收件入口才生成笔记。
- 聊天写入经统一 Vault 服务提交 Git，并登记来源消息 ID 与归档任务；Git 再次发现该提交时不得重复创建任务。
- 消息网关负责交互，Obsidian 保存长期知识；持久化消息与任务映射使用户能追问进度。
- 笔记链接同时提供标题与相对路径；客户端支持时附 Obsidian URI，不能假定聊天平台能直接打开本地文件路径。

平台接入范围：

| 渠道 | 拟定接入 | 待验证事项 |
|---|---|---|
| QQ | QQ 开放平台机器人，借鉴 XingtuBot 的消息分发与命令扩展方式 | 账号资质、可用会话类型、消息格式、主动通知与回复限制 |
| 飞书 | 应用机器人用于双向交互；群自定义 webhook 可单独作为通知出口 | 应用权限、事件订阅、回调连接方式、卡片能力 |
| 钉钉 | 应用机器人接收消息，评估 Stream 或 HTTP 回调 | 应用权限、回复/主动发送能力、会话凭据有效期 |

飞书自定义群机器人只提供通知能力，双向交互需要应用机器人；钉钉应用机器人支持 Stream 或 HTTP 接收。接入时按实际平台能力配置，不把单向 webhook 当成完整消息网关。[飞书官方说明](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot)、[钉钉接收消息](https://open-dingtalk.github.io/developerpedia/docs/learn/bot/appbot/receive/)

## 4. 产品交互与信息组织

### 4.1 入口与操作

- **日常记录：** 想法写入 Obsidian Inbox，Git 同步后后台自动整理归档；标记暂停归档可保留正在编辑的笔记。
- **日常阅读：** Obsidian 查看个人笔记和自动保存的一手信息，推送渠道接收简报和提醒。
- **主动交办：** 用户表达目标并提供材料，例如“整理今天的收件箱”“跟踪 Agent Security 论文”。首版保留 CLI，并接入一个消息渠道；QQ、飞书和钉钉作为可扩展入口，图形界面后续按需要设计。
- **审核处理：** 集中查看待确认事项，支持查看依据、修改、确认、退回和暂缓。
- **偏好设置：** 管理关注方向、信息源、推送时间、数量上限、提醒阈值和可操作范围。

这些是统一的交互能力，具体承载形式在首版交互设计中确定。

### 4.2 核心内容对象

| 对象   | 用户看到什么             | 可以做什么              |
| ---- | ------------------ | ------------------ |
| 信息条目 | 标题、来源、时间、摘要、相关性、证据 | 查看原文、收藏、转任务、反馈无用   |
| 任务   | 目标、进度、截止时间、结果或阻塞原因 | 补充材料、暂停、取消、重试、查看结果 |
| 审核事项 | 要执行的动作、具体内容、依据和影响  | 编辑、确认、退回、暂缓        |
| 知识笔记 | 正文、标签、关联和原始来源      | 编辑、关联、调整目录、撤销归档         |
| 周期报告 | 本周期事实、变化、问题和建议     | 核对、修订、转为下周期计划      |

### 4.3 用户可见状态

任务显示为：待开始、处理中、待你确认、已完成、失败、已暂停或已取消。失败需要说明原因和可采取的操作；部分完成时列出已完成项与剩余项。

“Agent 已生成答案”与“平台已成功提交”分别呈现。已确认内容被修改后重新进入审核，审核记录指向实际执行版本。

### 4.4 推送与反馈

- 普通信息合并成定时简报，数量和时段可配置。
- 临近截止、余额低于阈值、任务需要人工处理等按规则提醒。
- 同一事件合并重复来源，避免重复提醒；新进展明确标出变化。
- 支持有用、无用、减少此类、继续关注反馈，用户可随时修改偏好。
- 信息标明来源和更新时间；未获得最新数据时显示最后成功时间。

### 4.5 功能配置与后续扩展

- 用户可分别配置笔记整理、论文、校园和报告等功能的来源、触发规则与运行状态。
- 功能暂停后保留已有笔记和任务记录。
- 核心流程稳定后，再设计模块注册、依赖管理和独立插件安装；本阶段先确定功能边界与公共服务。

## 5. 首版范围与演进计划

以下为建议顺序，校园接口同时做小规模可行性验证。

| 阶段       | 范围                                                                 | 验收重点                                         |

**首版交付：每天采集少量高质量来源，生成有原始链接的精选笔记与一次推送；Inbox 笔记在 Git 更新后自动整理归档，一手信息自动沉淀到同一 Vault。** 水电费接口验证通过后可提前加入首版；X 完整接入和知到提交不作为首版阻塞条件。

## 6. 首版验收标准

- 能完成一次“采集 → Codex 处理 → 精选笔记 → 推送”的完整流程。
- 精选条目均带可追溯来源，论文摘要注明基于摘要还是全文。
- 向 Inbox 提交一篇分类明确的笔记，后端发现 Git 更新后无需逐篇确认即可完成整理、归档和写回，本地同步后可见。
- 自动归档保留个人内容，修复受影响的笔记与附件链接；分类不明确的笔记留在 Inbox 并标明原因。
- 采集到的有效一手信息自动保存来源笔记，日报能跳转到笔记和原始材料。
- 系统自己的提交不形成循环；用户后续修改可被识别；处理中发生并发编辑时不会覆盖用户内容。
- 归档后推送失败可恢复，撤销归档后不会立即被自动归档回去。
- 同一批输入重复处理，不重复创建笔记或发送相同通知。
- 任务失败、来源过期和需要审核的情况可见，用户能找到处理入口。
- 服务重启能恢复任务；同步冲突不覆盖人工内容。
- 试用时记录每天阅读与整理耗时、有效信息比例、误报/重复提醒和实际转为行动的条目数，用于确定下一阶段优先级。具体目标值待试用建立基线后确定。

## 8. 核心代码架构草案

### 8.1 当前设计范围

核心目标是可靠完成三条路径：

1. Git 更新 → Inbox 整理 → 归档 → Git 同步。
2. 外部信息采集 → 筛选与摘要 → 来源笔记 → 消息推送。
3. 聊天交办 → 执行任务 → 必要时审核 → 结果回复。

采用 **Rust 常驻服务 + AgentBackend（首个实现 Codex）+ TaskStore 运行状态（默认 SQLite 实现，PostgreSQL 等后端预留接口）+ Obsidian/Git 内容存储**。先部署一个服务进程，Codex 由接入层管理；代码按职责组织，暂不确定业务插件 SDK、动态加载或独立服务拆分。

### 8.2 核心结构

```text
入口：CLI / Git 更新 / 定时器 / QQ·飞书·钉钉
                        ↓
             接收、身份校验、事件去重
                        ↓
              TaskService：创建任务
                        ↓
              SQLite 持久化任务状态
                        ↓
          Worker：领取任务、推进步骤、恢复
                  ↙             ↘
          确定性 Rust 操作      AgentService
                                  ↕
                            Codex + Rust 工具
                  ↘             ↙
               结果校验 / 变更计划
                        ↓
              自动执行或等待人工审核
                        ↓
            Vault / 外部动作 / 结果核验
                        ↓
              任务结果 + 待发送记录
                        ↓
              消息网关回复或主动推送
```

**所有入口进入同一任务系统。** 消息平台不直接操作 Vault，Git 检测器不直接启动随意命令；入口负责把输入交给核心服务。

### 8.3 Rust 代码布局

先采用一个 Cargo package，包含服务入口和可测试的 library，以 `mod` 划分职责。以下目录是逻辑边界，后续可以按实际需要提取为 workspace crate。

```text
ru41/
├── Cargo.toml
├── Cargo.lock
├── src/
│   ├── main.rs                 # 启动、装配、关闭
│   ├── lib.rs                  # 暴露内部可测试服务
│   ├── config.rs               # 配置加载与校验
│   ├── domain/                 # 任务、输入、结果、审核、笔记变更类型
│   ├── app/
│   │   ├── task_service.rs     # 创建、查询、取消与恢复任务
│   │   ├── worker.rs           # 领取任务并推进步骤
│   │   ├── agent_service.rs    # 上下文、Codex 调用与结果校验
│   │   ├── vault_service.rs    # 归档计划、冲突检查、写入与同步
│   │   ├── review_service.rs   # 审核版本与执行授权
│   │   └── delivery_service.rs # 结果入发送队列与投递状态
│   ├── workflows/
│   │   ├── inbox.rs            # Inbox 整理流程
│   │   ├── intelligence.rs     # 外部信息入库流程
│   │   └── assistant.rs        # 聊天交办流程
│   ├── adapters/
│   │   ├── codex/             # Codex 进程/会话、事件解析
│   │   ├── git/               # 远端同步、差异、提交、推送
│   │   ├── sqlite/            # 查询、事务与迁移
│   │   ├── markdown/          # frontmatter、双链、内容处理
│   │   ├── sources/           # RSS、论文、校园接口
│   │   └── messaging/         # QQ、飞书、钉钉协议适配
│   ├── ingress/               # CLI、定时扫描、消息接收入口
│   └── tools/                 # Codex 可调用的受限 Rust 工具
├── migrations/
├── prompts/                   # 分类、摘要、归档等任务说明
├── config/
└── tests/                     # 核心端到端场景与失败恢复
```

职责约束：

- `domain` 定义业务数据与状态规则，不引用具体数据库、消息平台和 Codex 协议类型。
- `app` 编排公共服务并实施权限、状态与一致性检查。
- `workflows` 明确业务步骤，复用公共服务；首版用明确函数和任务类型分发。
- `adapters` 处理外部协议和数据转换，不能自行决定业务成功或审核通过。
- `main` 负责创建并传入具体实现，不在业务代码中到处创建数据库连接或 Codex 客户端。
- 只对需要替换或模拟的边界定义小型 trait，如 Agent 接入、任务存储和消息发送；普通业务优先用 struct、enum 和函数。

### 8.4 先定义的数据对象

| 对象 | 核心内容 | 用途 |
|---|---|---|
| InputEvent | 事件 ID、来源、操作者、内容引用、接收时间、去重键 | 统一 Git、消息与定时输入 |
| Task | 任务 ID、类型、用户、输入、状态、当前步骤、重试时间 | 描述需要完成的工作 |
| TaskAttempt | 尝试 ID、领取标识、开始/结束时间、错误、Agent 运行引用 | 保留每次执行，不覆盖失败历史 |
| AgentRun | 所属任务、上下文版本、会话标识、输出、执行状态 | 管理 Codex 的一次运行 |
| Artifact | 笔记、摘要、草稿等产物引用、版本、来源 | 持久化生成结果 |
| ChangeSet | 目标文件、预期旧指纹、新内容、移动与链接变更 | 把生成结果转为可校验的写入计划 |
| Approval | 动作、内容版本、授权用户、有效期、决策 | 将确认绑定到实际执行内容 |
| Delivery | 目标渠道、接收者、内容版本、发送状态、平台回执 | 独立处理消息投递 |

聊天会话、任务和 Codex 会话各自保存标识：一个聊天可发起多个任务，一个任务可以有多次 Agent 运行。不能把一条聊天消息、一次 Codex 返回和整个任务完成当成同一件事。

### 8.5 任务状态与恢复

建议状态：`queued`、`running`、`waiting_approval`、`waiting_input`、`retry_scheduled`、`paused`、`succeeded`、`failed`、`cancelled`。

- 接收事件和创建任务在同一数据库事务中落库，重复事件返回已有任务。
- Worker 通过事务领取任务，记录领取标识和租约；限制同时运行的 Codex 数量。
- Agent 运行期间不长期持有数据库事务或 Vault 写锁。
- 服务重启后回收过期任务租约，从已记录步骤恢复；动作状态不明时先核验外部结果。
- 执行写操作前复核领取标识与当前状态，防止旧 Worker 在任务转交后继续提交结果。
- 网络故障等可恢复错误按退避策略重试；权限、格式或来源问题进入待处理或失败。
- 暂停与取消在步骤边界生效，必要时终止 Agent 进程；已发生的外部动作不能假装被取消。
- 业务完成和通知成功分开记录，消息发送失败不导致重新归档或重新提交作业。

SQLite 保存任务、事件、尝试、审核、来源游标、笔记处理指纹和发送队列。持久化事件记录用于恢复与追踪；首版不建立完整事件溯源框架或消息中间件。

### 8.6 Agent 底座与 Rust 的边界

- Codex 负责理解、推理、分类、摘要、草稿及任务内的工具使用。
- Rust 负责定时与触发、持久状态、参数和权限检查、数据计算、正式写入与结果核验。
- AgentService 为每个任务构造限定上下文：目标、材料、相关笔记、目录规则、可用工具和结果结构。
- 输出按任务类型定义结构。例如归档输出分类、目标路径、整理文本、标签与链接建议，不只返回一段自由文本。
- Codex 的“完成”仅代表一次 Agent 运行结束；任务成功由 Rust 检查实际产物和操作结果后判定。
- 无需推理的步骤直接执行 Rust 代码，例如余额阈值判断、内容指纹比较和通知去重。

接入层先验证批处理路径，再按交互需求评估持续会话；其具体协议封装在 `adapters/codex` 内。工具经 `tools` 调用应用服务，不能绕过 Vault 写入和审核规则。Agent 使用必要资料与草稿工作区，正式平台凭据留在执行端。

#### 底座接入通用性

- `AgentBackend` 定义底座描述与执行接口，Codex 原生协议留在适配器内。
- `BackendRegistry` 在启动时注册底座；任务显式绑定后端 ID 和执行契约，不自动跨底座降级。
- 每次尝试记录后端、模型、会话 ID、结果与错误；会话 ID 不跨底座复用。
- 当前实现 `analysis_v1`：校验并保存结构化分析结果。工具、恢复和审核能力后续按真实需求扩展，不能假定所有底座相同。
- 两个模拟底座用于验证同一 Worker 的路由和隔离，真实接入当前只有 Codex。
- 底座接口、业务模块和消息渠道分别设计，新增底座尽量不影响已有业务。

### 8.7 Vault 的唯一写入入口

VaultService 管理所有笔记变更，Git 同步器与它共用写入协调机制。

1. 读取已同步快照，记录提交 ID、笔记 ID 和内容指纹。
2. 在快照上生成 ChangeSet，保留人工内容和来源信息。
3. 写入前重新同步并核对所有受影响文件；内容已变化则重新分析或进入冲突处理。
4. 串行应用文件移动、正文和关联链接变更，记录操作进度；多文件写入按可恢复步骤执行，不假设整个文件系统事务原子完成。
5. 只提交本次任务涉及的文件，Git 提交包含任务标识。
6. 推送成功后记录同步完成；推送失败保留既有提交，重试同步而不是重新生成内容。

数据库事务与 Git 操作不能合为一个原子事务，因此每一步都要能通过任务标识、提交 ID 和文件指纹判断是否已发生。归档撤销生成经过冲突检查的反向变更，保留后续人工编辑。

自己的写回依据任务标识与输出指纹去重；不能简单忽略机器人作者的所有提交，以免漏掉混合变更。

### 8.8 消息网关与其他入口

- QQ、飞书、钉钉统一转换为消息事件，带渠道、机器人实例、租户（如有）、会话、发送者和消息 ID。
- 平台用户显式绑定个人身份；上下文按用户与会话隔离，群聊权限单独判断。
- 消息持久化后及时响应平台，长任务先回复已接收与任务 ID，结果异步发送。
- 固定命令直接分发，自然语言交给 AgentService；“记一下”进入与 Git Inbox 相同的整理流程。
- 回复使用统一目标和消息内容，渠道适配器负责平台格式、连接、限流和回执。
- 卡片不可用时降级到文本与确认码，审核仍绑定授权用户、任务和具体内容版本。
- 主动发送受限、发送超时、重复回调等由投递服务处理；不支持的能力明确反馈。
- CLI 和定时器也调用 TaskService，不能各自维护另一套执行逻辑。

### 8.9 数据存放与运行方式

| 位置 | 内容 |
|---|---|
| SQLite | 运行状态、任务、审核、游标、指纹和投递队列 |
| Obsidian Vault | 个人想法、来源笔记、知识、项目、计划与报告 |
| Git | Vault 版本与双向同步记录 |
| 任务工作目录 | Agent 输入快照、草稿和临时产物 |
| 独立媒体存储 | 原始照片、音视频及大型资产 |
| 受限凭据存储 | Codex、Git 和平台认证信息 |

笔记落点沿用现有 Vault 分类，机器状态不进入笔记正文。日志按事件、任务、Agent 运行和操作 ID 关联，屏蔽凭据与不必要的私人内容。

首版一个服务内运行入口监听、Worker、Vault 写入与投递循环，设置有界队列和并发上限。退出时停止接收新工作，保存进度，处理正在运行的任务与子进程。断电后的恢复以持久状态为准。

### 8.10 核心实现与验证顺序

1. **任务骨架：** CLI 创建、查询、取消任务，SQLite 保存和恢复状态。
2. **Codex 接入：** 一个任务完成材料读取和结构化输出，验证超时、失败与输出校验。
3. **Inbox 闭环：** Git 新提交触发任务，生成 ChangeSet、自动归档、提交并推送。
4. **恢复验证：** 重复事件、Agent 结束后崩溃、部分文件写入、提交后未登记、推送失败和并发编辑。
5. **消息入口：** 一个渠道复用任务服务完成记录想法、查询进度和接收结果。
6. **第二种业务：** 论文或 RSS 来源进入同一笔记与推送流程，验证公共服务边界。

核心验收以真实结果为准：没有丢笔记、没有重复动作、能恢复、能追溯。完成两个不同业务流程后，再判断哪些边界值得提取为独立 crate 或模块接口。

## 9. 后续模块化与插件化议题

核心验证后讨论以下内容，当前不锁定接口或加载机制：

- 哪些业务单元需要独立启停、配置、版本和数据迁移。
- 从现有流程中提取任务处理、来源采集与工具注册接口。
- 是否需要 Cargo workspace，以及哪些包应独立构建和测试。
- 是否存在“不重编译主程序即可安装新功能”的真实需求。
- 独立插件的通信、生命周期、兼容性与权限隔离。

模块化目标是让新业务复用稳定核心；插件化范围由实际交付和运行需求决定。
