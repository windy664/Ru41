# 校园跑进度与规则

## 查询（经 CLI）

- `ru41 campusrun status`：学期进度——有效里程/总里程、有效次数、**学期目标里程**、目标次数、是否达标、学期剩余天数。
- `ru41 campusrun rules`：规则面——单次门槛（距离取服务端 `policy.minDistance`、时长取上次记录的规则，各门课不同）、补跑限制（最多往前几天、随机时刻窗口，以命令输出为准）、必过点、围栏。
- `ru41 campusrun records [条数]`：最近记录表。
- `ru41 campusrun cheat`：违规名单状态。
- `ru41 campusrun all`：上面几样一起。

输出是一个 JSON 字符串，里面装的是 Markdown（`\n` 是换行）——解析出正文再整理回复。

## 读数时必须注意

1. **接口没给公里目标时，不许说「已达标」**（2026-11-23 实测）：
   上游 `semesterTargetDis` / `semesterTargetCount` 在真实响应里**是空的**，
   只剩一个 `semesterGoal=1` —— 而这个字段的单位是**米**（pace-forge 源码
   `api/semester.rs` 的 `target_dis = num(["semesterGoal", ...])`，
   实测样本 `semesterGoal: 60000` 即 60 km），所以 1 就是 **1 米** ≈
   这个课**没设记分跑学期目标**。
   命令输出会写「服务端未给出公里目标」+「不能据此说『已达标』」——
   **照念这两行**，并把学期跑量要求交给用户在 App 上核对，
   **不要**自己拿 `semesterGoal` 或 `targetDis` 算达标。
   （此前就是拿 1（米）当公里算出「已达标」，是错的。）
   目标次数在 `targetCount`（0 = 不计次），这个可以照念。
   **工具给什么就转述什么**：工具没解释的，agent 也不要替它解释。
   插件配置里的 `semester_target_km` 是**App 口径的目标**（接口读不到，人工抄进去的），
   输出里会写成「学期跑量目标（**App 口径**，接口不给）：N km」+「还差 X km」——
   转述时**要带上这个口径说明**，别把它说成服务端给的。
2. **单次门槛 ≠ 学期目标**：单次门槛（最少多少公里/多少分钟）**各门课不同**，
   以命令输出里的「服务端门槛」和「上次提交的判定」为准，不要自己套固定数字。
3. **有效里程才算成绩**：命令会同时给「有效里程」与「共 X km」，回答时要说清用的是哪个。
   ⚠️ 另外注意「**有效次数 0**」：命令会提示「里程在涨，但『有效次数』是 0 ——
   这两个口径不同源，**服务端没解释**」。照念这句话就行，**别替服务端猜原因**
   （实测有 4 条记录 complete=true，次数仍是 0，所以「没跑够」之类的解释是不成立的）。
   另一条独立事实：单次距离要达到当次任务的最小距离（记录详情里的 selDistance，
   各任务不同），否则**那一条**会被判未完成。
4. **命令报错就照实说**：没令牌、连不上控制台、令牌不对、登录态失效，命令都会直接报错——
   把原因转述给用户，**不要编一个进度数字**。

## 跑一次（用户明确要求时）

**这个插件能提交**（不是只读）——但提交是两步，且必须有用户明确同意。

- `ru41 campusrun plan --laps 3` 或 `--km 1.2`：**预演**（生成轨迹 + 八类自检，**不提交**）。
  圈数会自动换算：1 圈 = 400 m（第 1 道），3 圈 = 1.2 km。
  **能不能跑由工具自己的 preflight 说了算**，插件不自己判——预演没过就把工具给的原因原样念出来。
  输出里的「服务端最小里程」是服务端的要求，转述给用户，别自己加判定。
- 预演输出里若出现「自检被拦下」，**不要提交**，如实转述被拦的原因。
- 真正的提交是**两步**：`ru41 campusrun submit --laps 3` 只登记一条待确认的提交（返回确认口令），
  用户明确说「提交/确认」之后才 `ru41 campusrun confirm <口令>`。
  （注意：`ru41 campusrun run` 会被宿主当成 tracker 的长驻任务抢走，**别用 run**，用 submit。）

## 什么时候跑（**你自己从话里读**，配置里没有这一项）

插件**不猜**「什么时候跑」，配置里也没有这一项——**时态由你从用户这句话里读出来**，
再翻译成参数传进去。

| 用户的话 | 传什么 | 含义 |
| :--- | :--- | :--- |
| 「帮我跑」「跑三圈」（**没提时间**） | 不带时间参数 | 默认 = **当天随机、几天前 0**（用户给的推荐参数） |
| 「补一下半小时前那次」 | `--ago 30` | 补跑 30 分钟前那次 |
| 「今天九点那次」 | `--at 09:00` | 补跑今天九点那次 |
| 「昨天晚上八点那次」 | `--at 20:00 --days 1` | 补跑昨天 20:00 |
| 「前天那次」（不指定钟点） | `--rand --days 2` | 补跑前天某个随机时刻 |
| 「就当刚跑完」 | `--now` | 刚跑完（工具/Web 端的默认档） |

- 起跑时刻**由服务端算**（`/api/starttimes`），你只把意图传过去；服务端有时会**收窄**这个时段，
  输出里会写「服务端把这个时段收窄过」，照念。
- **「半小时后帮我跑」是未来**：记录只能补**已发生**的跑（工具规则：开始+用时 ≤ 现在，最多往前 3 天），
  所以「半小时后」要么用宿主的一次性提醒到点再跑（`ru41 todo add --title "校园跑" --remind "YYYY-MM-DD HH:MM"`，
  到点 `ru41-todo-remind` 容器会发消息提醒你），要么把话说清楚：现在跑 / 补跑哪一次。
  **别把未来时间硬塞成补跑。**
  **没有用户明确同意，不要走到 confirm 那一步。**
